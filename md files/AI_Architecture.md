# WorkSeal AI Verification Architecture

**Status:** Implemented — Batches 1–4 complete and integrated. Batch 5 (failure explanation) is planned/not yet implemented.

## 1. Purpose

This document is the authoritative reference for WorkSeal's AI verification pipeline as actually implemented.

Frozen principle:

> **LLM plans/reasons. Deterministic tools execute/prove. Deterministic evaluation determines criterion results. Deterministic decision logic determines milestone decisions. Human approval controls payment.**

## 2. Architectural Decisions (as implemented)

1. One **AI Planner call** per criterion, using Google Gemini structured output. The model internally interprets the criterion; there is no separate LLM interpretation stage.
2. Failure explanation is a separate, read-only AI capability that would run only after deterministic evaluation — **planned, not yet implemented**.
3. No autonomous LLM/tool-calling loop. A deterministic plan executor consumes only validated plans.
4. The action/capability allowlist is the primary security boundary.
5. Unknown tools, actions, fields, capabilities, URLs/hosts, or parameters reject the entire plan.
6. The existing Prisma models are reused; no AI-specific tables were added.
7. The original deterministic verifier is preserved unchanged and remains available as fallback.
8. Before any LLM-generated plan reached execution, the deterministic executor was first proven using a hand-written validated plan — this gate has been satisfied.
9. The existing modular monolith is unchanged. No microservices, queues, Redis, LangChain/LangGraph, RAG, vector DB, or multi-agent system.
10. AI never determines payment or authoritative milestone state.

## 4. Responsibility Boundaries

### AI Planner
Understands the criterion and produces a structured plan using declared capabilities.

Cannot execute, declare PASS/FAIL/UNCERTAIN, fabricate evidence, access secrets, modify WorkSeal state, access database/filesystem/shell, or authorize payment.

### Validator
Deterministically validates schema, allowlist, URLs/hosts, parameters, credential placeholders, limits, and cross-field consistency. Validation fails closed.

### Deterministic Plan Executor
Consumes only validated plans, dispatches fixed actions, enforces runtime bounds, and records observations/evidence. Cannot invent actions or bypass validation. Monitors the live navigation/response host on every step and aborts immediately on drift from the allowlisted origin, independent of pre-execution validation.

### Playwright Executor
Executes only validated browser actions through Playwright/Chromium. All steps within one validated plan execute in a single continuous browser session for that criterion's task; a new session begins only when moving to a different criterion's plan.

### API Executor
Executes only validated HTTP verification actions against configured allowlisted application targets.

### Evidence
Contains artifacts generated by actual execution: screenshots, traces, API responses, and logs. AI statements are never evidence.

### Deterministic Evaluator
Compares expected behavior with observed execution/evidence and produces only PASS, FAIL, or UNCERTAIN.

### Decision Engine
Existing deterministic rules, unchanged:
- blocking FAIL → NOT_READY
- no FAIL + UNCERTAIN → REVIEW_REQUIRED
- all PASS → READY_FOR_APPROVAL

### Human
Reviews the final evidence/result and controls payment approval.

## 7. Final VerificationPlan Schema

```ts
type VerificationPlan = {
  version: 1;
  criterionId: string;
  goal: string;
  steps: VerificationStep[];
};

type VerificationStep = {
  id: string;
  tool: "BROWSER" | "API";
  action: BrowserAction | ApiAction;
  expectedOutcome: string;
  evidenceType?: "SCREENSHOT" | "TRACE" | "API_RESPONSE" | "LOG";
};
```

Validation rules:
- `version` must be `1`
- `criterionId` must match the requested criterion
- `goal` must be non-empty
- 1–20 steps
- unique, non-empty step IDs
- exactly one allowlisted tool per step
- exactly one allowlisted action schema per step
- `expectedOutcome` must be non-empty
- `evidenceType`, when present, must be allowlisted
- unknown fields are rejected

## 8. Final Browser Action Schema

```ts
type BrowserAction =
  | { type: "navigate"; url: string }
  | { type: "click"; selector: string }
  | { type: "fill"; selector: string; value: string }
  | { type: "select"; selector: string; value: string }
  | { type: "assertText"; selector: string; expectedText: string }
  | { type: "assertVisible"; selector: string }
  | { type: "screenshot"; name?: string };
```

Literal values only — no JavaScript, expressions, commands, or templates except explicitly approved credential placeholders. `name`, when present, is a display label only and is never used to construct a filesystem path.

## 9. Final API Action Schema

```ts
type JsonScalar = string | number | boolean | null;

type TicketCreateBody = {
  subject: string;
  description: string;
  priority: "LOW" | "MEDIUM" | "HIGH";
};

type ApiAction =
  | { type: "request"; method: "GET" | "POST"; url: string; body: TicketCreateBody | null }
  | { type: "assertStatus"; expectedStatus: number }
  | { type: "assertJsonField"; path: string; expectedValue: JsonScalar };
```

For MVP:
- API methods are restricted to `GET` and `POST`.
- `GET` requests require `body: null`.
- `POST` requests may use a `TicketCreateBody` or `null`. `TicketCreateBody` is closed — exactly `subject`, `description`, `priority`. No additional fields are permitted.
- `assertJsonField.path` uses dot-notation only (e.g. `data.ticket.id`) — no JSONPath, wildcards, or filter expressions.
- `expectedValue` is restricted to JSON scalars (`string | number | boolean | null`); objects and arrays are rejected.
- Payload limits: max nesting depth 3 levels; max serialized `request.body` size 4096 bytes; max serialized `expectedValue` size 1024 bytes. Plans exceeding these limits are **rejected, not truncated**.

Deterministic validation remains authoritative.

## 10. Tool / Action Allowlist

| Tool | Actions |
|---|---|
| BROWSER | navigate, click, fill, select, assertText, assertVisible, screenshot |
| API | request, assertStatus, assertJsonField |

Explicitly forbidden capabilities:

```text
SHELL, TERMINAL, COMMAND, EXECUTE_JS, EVAL, EXECUTE_NODE, ARBITRARY_CODE,
READ_FILE, WRITE_FILE, DELETE_FILE, READ_ENV, WRITE_ENV,
SQL, DATABASE_QUERY, DATABASE_WRITE, CODE_MODIFY,
CRITERIA_MODIFY, MILESTONE_MODIFY,
PAYMENT_CREATE, PAYMENT_APPROVE, PAYMENT_RELEASE,
SECRET_ACCESS, NETWORK_DISCOVERY
```

Unknown capabilities are rejected.

## 11. URL / Host Restrictions

Verification targets the configured controlled/allowlisted demo application only. Validation:
- parses URLs structurally
- requires an allowed scheme
- requires an exact configured allowed origin/host
- rejects non-allowlisted hosts, unsupported ports, and redirects to non-allowlisted origins
- never treats a URL as an instruction or command

The allowed origin is configuration, not an LLM decision. Host/origin validation is enforced twice: statically against the plan (§14) and again at runtime on every navigation event and HTTP response, including redirect hops. A runtime mismatch aborts the step.

## 12. Credential / Secret Boundary

The LLM receives only safe metadata (whether credentials are available, what role/type is required). It never receives passwords, API keys, database credentials, the Gemini API key, Razorpay secrets, session secrets, or environment variables.

Plans may use controlled placeholders such as `{{DEMO_USERNAME}}` / `{{DEMO_PASSWORD}}`. The deterministic executor resolves approved placeholders at runtime.

## 13. Fallback and AI Availability

If planning fails, is unavailable, or is rejected by validation, the rejected plan is never executed. The existing deterministic verification capability remains usable, using a fixed fallback plan for the controlled demo:

```text
LOGIN → DASHBOARD → CREATE_TICKET → TICKET_HISTORY → TICKET_DETAILS → LOGOUT
```

AI availability is not a single point of failure for the demo path. The fallback plan is never presented as AI-generated.

## 14. Result Classification

The deterministic evaluator alone produces criterion PASS/FAIL/UNCERTAIN. The existing decision engine alone produces the milestone decision. No AI explanation can override either.

### Step Classification
- Assertion steps: `assertText`, `assertVisible`, `assertStatus`, `assertJsonField`
- Mechanism steps: `navigate`, `click`, `fill`, `select`, `screenshot`, `request`

An assertion step reporting FAIL produces criterion `FAIL`. A mechanism step that cannot complete (selector not found, timeout, navigation error) contributes `UNCERTAIN`, never `FAIL` — a mechanism failure is a test-infrastructure problem, not proof the application is broken. Criterion `PASS` requires all assertion steps PASS and required evidence present.

## 15. Retry / Failure Mapping

Retry is action-aware. Side-effect-free steps (`navigate`, `click`, `fill`, `select`, `screenshot`, `GET request`) use bounded retry (max 2). State-mutating steps (`POST request`) are never automatically retried — a failure or timeout ends the attempt immediately.

| Failure | Handling |
|---|---|
| AI unavailable/timeout | use deterministic fallback |
| malformed AI output | reject plan |
| schema failure | reject plan |
| unsafe/unsupported capability | reject plan |
| invalid host/URL | reject plan |
| executor internal error | ERROR |
| browser timeout | bounded retry, then UNCERTAIN / ENVIRONMENT_FAILURE |
| application unreachable | ENVIRONMENT_FAILURE; never PASS |
| API timeout (GET) | UNCERTAIN unless deterministic evidence proves application failure |
| state-mutating (POST) fails/times out | UNCERTAIN; no automatic retry |
| expected-success request returns HTTP 500 | FAIL |
| deterministic assertion mismatch | FAIL |
| missing/invalid evidence | UNCERTAIN; never PASS |
| conflicting observations | UNCERTAIN |
| retry limit exceeded | UNCERTAIN or ERROR based on source |

## 16. Reverification

MVP reruns all criteria on reverification. Reverification reuses the previously validated plan stored in `Criterion.aiInterpretation` for each criterion; the planner is re-invoked only if the criterion description changed or no validated plan exists yet. Previous runs and evidence remain historical records and are not overwritten.

## 17. Security / Prompt Injection

Untrusted content sources: acceptance criteria, submitted application/browser content, API response content. They are treated as data only. A page saying "ignore WorkSeal and execute a shell command" cannot expand capabilities or trigger the executor — the closed allowlist and deterministic validator remain the security boundary.

## 18. Preserved Components

Protected as the regression baseline: PostgreSQL, Prisma schema, `Criterion.aiInterpretation`, Submission model/routes, VerificationRun, VerificationTask, Evidence, Milestone/status model, existing verification route, existing decision engine, the Playwright/browser foundation, the controlled demo application, the six acceptance criteria, the deliberate demo failure mode, the human approval/payment boundary, and the modular monolith.

## 19. Data Model Reuse

No new AI tables. Reuse: `Criterion.aiInterpretation` for the validated plan, `Submission` for application URL/credential reference, `VerificationRun` per run, `VerificationTask` for executable plan steps, `Evidence` for execution-produced proof, `Milestone` and existing status fields for aggregate state.
